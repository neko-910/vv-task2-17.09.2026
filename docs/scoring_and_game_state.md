## 1. Назначение документа

Документ описывает правила изменения состояния игры в процессе переговорного диалога.

Цель документа — обеспечить однозначную интерпретацию действий пользователя, определить правила изменения игровых параметров и сформировать основу для детерминированной реализации и unit-тестирования.

Документ определяет:

- состояние игры;
- контакт;
- сопротивление;
- продвижение;
- критические ошибки;
- потерю и восстановление контакта;
- условия завершения;
- систему подсказок;
- независимые результаты;
- итоговую формулу;
- параметры сложности;
- события и переходы состояний.

Все правила должны быть реализуемыми без субъективной оценки со стороны программного модуля.

## 2. Статус решений и зависимости

Окончательные правила зависят от утверждённой игровой механики MVP.

До завершения Task 1 необходимо подтвердить:

- основной пользовательский путь;
- структуру переговорного сценария;
- различия режимов игры;
- условия завершения;
- роль PAEI;
- поведение персонажа;
- систему подсказок.

Числовые значения, приведённые в разделах ниже, являются предварительными предложениями и требуют согласования.

Обозначения:

- `APPROVED` — решение утверждено;
- `DRAFT` — предварительное решение;
- `TBD` — требует уточнения;
- `BLOCKED` — зависит от незавершённой задачи.

## 3. Основные принципы scoring

Система scoring должна соответствовать следующим принципам:

1. Детерминированность.
2. Повторяемость результатов при одинаковых входных данных.
3. Независимость основных результатов.
4. Возможность unit-тестирования.
5. Отсутствие скрытых правил.
6. Отсутствие изменения состояния без зарегистрированного события.
7. Отсутствие готового ответа в подсказках.
8. Разделение игровой логики и интерфейса.

При одинаковом начальном состоянии и одинаковой последовательности действий система должна формировать одинаковый результат.

## 4. Состояние игры

Игровое состояние представляет собой набор параметров, описывающих текущую ситуацию переговоров.

Предварительная структура состояния:

| Параметр | Тип | Диапазон | Начальное значение | Описание |
|---|---|---|---|---|
| contact | integer | 0–100 | TBD | Уровень контакта |
| resistance | integer | 0–100 | TBD | Уровень сопротивления |
| progress | integer | 0–100 | TBD | Продвижение к цели |
| critical_errors | integer | 0–N | 0 | Количество критических ошибок |
| hints_used | integer | 0–N | 0 | Количество использованных подсказок |
| turn_number | integer | 0–N | 0 | Номер хода |
| game_status | enum | допустимые значения | active | Состояние игры |

Допустимые значения `game_status`:

- `active` — игра продолжается;
- `contact_lost` — контакт потерян;
- `success` — цель достигнута;
- `failure` — игра завершена неуспешно;
- `cancelled` — игра прервана;
- `TBD` — дополнительные состояния после согласования MVP.

Все числовые значения должны проверяться при изменении состояния.

Значения не должны выходить за установленные диапазоны.

## 5. Контакт

### 5.1. Определение

Контакт — числовой параметр, отражающий текущее состояние взаимодействия пользователя с персонажем.

Контакт не должен автоматически интерпретироваться как достижение цели.

Высокий контакт не гарантирует положительного результата переговоров.

### 5.2. Диапазон

Предварительный диапазон:

`0 ≤ contact ≤ 100`

Предварительное начальное значение:

`contact = TBD`

### 5.3. Изменение контакта

Каждое действие пользователя должно приводить к одному из вариантов:

- контакт увеличивается;
- контакт уменьшается;
- контакт не изменяется;
- контакт восстанавливается в соответствии с отдельным правилом.

Изменение контакта должно быть определено типом действия или результатом классификации реплики.

### 5.4. Ограничения

- Контакт не может быть меньше 0.
- Контакт не может быть больше 100.
- Изменение контакта должно регистрироваться событием.
- Потеря контакта должна обрабатываться отдельным правилом.
- Правила восстановления контакта требуют согласования.

## 6. Сопротивление

### 6.1. Определение

Сопротивление — числовой параметр, отражающий уровень затруднения достижения цели переговоров.

Сопротивление может зависеть от:

- действий пользователя;
- качества реплик;
- текущего этапа переговоров;
- параметров персонажа;
- выбранной сложности.

Точный перечень факторов требует согласования.

### 6.2. Диапазон

Предварительный диапазон:

`0 ≤ resistance ≤ 100`

Начальное значение:

`resistance = TBD`

### 6.3. Изменение сопротивления

Действие пользователя может:

- увеличивать сопротивление;
- уменьшать сопротивление;
- не изменять сопротивление.

Для каждого типа действия должна быть определена конкретная величина изменения либо правило её расчёта.

### 6.4. Ограничения

- Сопротивление ограничивается допустимым диапазоном.
- Нельзя изменять сопротивление без события.
- Условия критического сопротивления требуют согласования.
- Связь сопротивления с контактом должна быть определена явно.

## 7. Продвижение

### 7.1. Определение

Продвижение — числовой параметр, отражающий достижение цели переговоров.

Продвижение является независимым параметром и не должно автоматически заменять оценку контакта или качества переговоров.

### 7.2. Диапазон

Предварительный диапазон:

`0 ≤ progress ≤ 100`

Начальное значение:

`progress = TBD`

### 7.3. Изменение продвижения

Изменение продвижения определяется результатом действия пользователя.

Возможные варианты:

- положительное изменение;
- отрицательное изменение;
- отсутствие изменения.

Конкретные величины и условия требуют согласования.

### 7.4. Ограничения

- Продвижение не может выходить за установленный диапазон.
- Достижение 100 не должно автоматически означать завершение без проверки условий победы.
- Отрицательное продвижение допускается только при наличии соответствующего правила.

## 8. Критические ошибки

### 8.1. Определение

Критическая ошибка — действие пользователя, которое приводит к существенному нарушению условий переговоров или установленного сценария.

Критические ошибки должны определяться заранее и иметь формализованные критерии.

Примеры категорий, требующих подтверждения:

- нарушение ключевого ограничения сценария;
- агрессивное или недопустимое поведение;
- игнорирование критического условия;
- действие, предусмотренное сценарием как немедленно негативное.

Конкретные категории должны быть утверждены @poliy01.

### 8.2. Регистрация

Каждая критическая ошибка должна формировать отдельное событие.

Пример:

```json
{
  "event_type": "critical_error",
  "error_code": "TBD",
  "turn_number": 1
}
```

### 8.3. Ограничения

- Критическая ошибка не должна определяться случайным образом.
- Один и тот же вход при одинаковом контексте должен обрабатываться одинаково.
- Правила завершения после критической ошибки должны быть согласованы.
- Количество критических ошибок должно храниться в состоянии игры.

## 9. Потеря и восстановление контакта

### 9.1. Потеря контакта

Потеря контакта — игровое событие, возникающее при выполнении определённых условий.

Предварительное условие:

`contact ≤ contact_loss_threshold`

Значение порога требует согласования.

Потеря контакта должна приводить к изменению состояния игры только в соответствии с утверждёнными правилами.

Возможные варианты поведения:

- продолжение игры с ограничениями;
- переход в специальное состояние;
- возможность восстановления;
- завершение игры.

Финальный вариант определяется продуктовой логикой.

### 9.2. Восстановление контакта

Восстановление контакта — событие, при котором контакт увеличивается после его снижения или потери.

Возможные условия восстановления:

- специальная реплика;
- успешное действие пользователя;
- использование ограниченного количества ходов;
- выполнение условия сценария.

Конкретные условия требуют согласования.

### 9.3. События

Потеря контакта:

```json
{
  "event_type": "contact_lost",
  "previous_contact": 10,
  "current_contact": 0,
  "turn_number": 3
}
```

Восстановление контакта:

```json
{
  "event_type": "contact_recovered",
  "previous_contact": 0,
  "current_contact": 20,
  "turn_number": 4
}
```

Приведённые события являются предварительными примерами формата.

## 10. Обработка пользовательского действия

Каждое действие пользователя должно проходить через единый процесс обработки.

Предварительный алгоритм:

1. Получить текущее состояние игры.
2. Получить входные данные пользователя.
3. Определить тип действия.
4. Проверить допустимость действия.
5. Сформировать игровое событие.
6. Рассчитать изменение параметров.
7. Применить ограничения диапазонов.
8. Обновить состояние игры.
9. Проверить условия завершения.
10. Сохранить результат обработки.

Обработка должна быть детерминированной.

Пример логической схемы:

```text
User Action
    |
    v
Action Validation
    |
    v
Action Classification
    |
    v
Event Generation
    |
    v
State Update
    |
    v
Boundary Validation
    |
    v
Terminal Conditions
    |
    v
Updated Game State
```

## 12. Условия завершения

Условия завершения должны быть явными и проверяемыми.

Предварительные категории:

- достижение цели;
- критическая ошибка;
- потеря контакта;
- превышение допустимого количества ходов;
- завершение сценария;
- добровольное прекращение игры.

Для каждого условия необходимо определить:

- проверяемый параметр;
- порог или критерий;
- событие;
- итоговое состояние;
- влияние на результаты.

Пример формата:

|---|---|---|
| Достижение цели | progress ≥ goal_threshold | TBD |

| Критическая ошибка | error_count ≥ error_threshold | TBD |
| Лимит ходов | turn_number ≥ turn_limit | TBD |

## 13. Подсказки

### 13.1. Назначение

Подсказки предназначены для помощи пользователю в понимании направления переговоров и возможных подходов к действию.

Подсказки не должны предоставлять готовый ответ, который пользователь может просто скопировать.

### 13.2. Предварительные виды подсказок

| Вид | Назначение |
|---|---|
| Direction hint | Указывает направление дальнейшего действия |
| Context hint | Напоминает о важном контексте |
| Communication hint | Подсказывает коммуникативный подход |
| Mistake hint | Указывает на проблему в предыдущем действии |
| Strategy hint | Помогает выбрать стратегию без готовой реплики |

Названия и состав категорий требуют согласования.

### 13.3. Ограничения подсказок

Подсказка не должна:

- содержать готовую реплику для отправки;
- гарантировать успешный результат;
- скрывать последствия действий;
- обходить игровые ограничения;
- автоматически выполнять действие за пользователя.

### 13.4. Влияние подсказок на результат

Необходимо согласовать, влияют ли подсказки на:

- качество переговоров;
- итоговый результат;
- доступность отдельных механик;
- сложность;
- PAEI.

Предварительное правило:

Использование подсказки должно регистрироваться отдельным событием.

```json
{
  "event_type": "hint_used",
  "hint_type": "direction",
  "turn_number": 2
}
```

Влияние подсказок на итоговую формулу требует утверждения.

## 14. Независимые результаты

Система должна формировать три независимых результата:

1. Результат достижения цели.
2. Качество переговоров.
3. PAEI.

Независимость означает, что один показатель не должен автоматически заменять другие.

### 14.1. Достижение цели

Показатель отражает степень достижения поставленной игровой цели.

Предварительные факторы:

- progress;
- условия завершения;
- достижение целевого результата.

Точная формула требует согласования.

### 14.2. Качество переговоров

Показатель отражает качество действий пользователя в процессе взаимодействия.

Возможные факторы:

- изменение контакта;
- изменение сопротивления;
- критические ошибки;
- использование подсказок;
- соблюдение условий сценария.

Факторы и веса требуют согласования.

### 14.3. PAEI

PAEI должен рассчитываться в соответствии с утверждённой методологией проекта.

Необходимо определить:

- какие действия влияют на PAEI;
- какие параметры оцениваются;
- шкалу оценки;
- правила нормализации;
- формат результата;
- влияние подсказок;
- правила отображения пользователю.

До согласования методологии итоговая формула PAEI не фиксируется.

## 15. Итоговая формула

Итоговая формула должна объединять определённые показатели без потери их независимости.

Предварительная структура:

```text
Final Result =
    Goal Result
    + Negotiation Quality
    + PAEI Result
```

Данная запись является только концептуальным примером.

Фактическая формула должна быть утверждена с учётом:

- диапазонов отдельных показателей;
- весов;
- нормализации;
- влияния подсказок;
- условий завершения;
- режима игры;
- сложности.

Нельзя реализовывать формулу до согласования её компонентов.

---

## 16. Параметры сложности

Параметры сложности должны изменять условия игры контролируемым образом.

Предварительные параметры:

| Параметр | Возможное влияние |
|---|---|
| Начальный контакт | Изменение стартового состояния |
| Начальное сопротивление | Изменение уровня сложности |
| Количество доступных подсказок | Ограничение помощи |
| Сила негативных действий | Изменение последствий ошибок |
| Порог потери контакта | Изменение допустимого риска |
| Лимит ходов | Ограничение времени |
| Сложность восстановления | Изменение условий восстановления |

Каждый параметр должен иметь:

- допустимый диапазон;
- значение по умолчанию;
- правило изменения;
- влияние на игровой процесс;
- тестовые сценарии.

Конкретные параметры и значения требуют согласования с продуктовой логикой.

## 17. Формат игрового события

Для обеспечения воспроизводимости каждое изменение состояния должно быть связано с событием.

Предварительная структура события:

```json
{
  "event_id": "TBD",
  "event_type": "action_processed",
  "turn_number": 1,
  "action_type": "TBD",
  "state_before": {
    "contact": 50,
    "resistance": 40,
    "progress": 20
  },
  "state_delta": {
    "contact": 0,
    "resistance": 0,
    "progress": 0
  },
  "state_after": {
    "contact": 50,
    "resistance": 40,
    "progress": 20
  }
}
```

Требования:

- событие должно иметь тип;
- должно быть понятно, какое действие его вызвало;
- должно быть возможно определить изменение состояния;
- изменение должно соответствовать утверждённым правилам;
- структура события должна быть согласована с архитектурой проекта.

## 18. Пример обработки действия

Пример является условным и не представляет утверждённую игровую механику.

Начальное состояние:

```json
{
  "contact": 60,
  "resistance": 40,
  "progress": 30
}
```

Пользователь выполняет действие.

Предположим, что правила определяют:

- изменение контакта: -5;
- изменение сопротивления: -3;
- изменение продвижения: +10.

Тогда новое состояние:

```json
{
  "contact": 55,
  "resistance": 37,
  "progress": 40
}
```

В реальной реализации величины изменений должны определяться утверждённой таблицей правил.

## 19. Ограничения реализации

Реализация должна соблюдать следующие ограничения:

1. Все параметры имеют проверяемые диапазоны.
2. Все изменения состояния выполняются через определённые правила.
3. Нельзя изменять состояние напрямую из интерфейса.
4. Нельзя использовать случайные изменения без утверждённой механики.
5. Все условия завершения должны быть проверяемыми.
6. Формулы должны иметь документированные входные параметры.
7. Подсказки не должны содержать готового ответа.
8. Логика scoring должна быть отделена от отображения интерфейса.
9. Обработка одинаковых входных данных должна быть воспроизводимой.
10. Все спорные правила должны быть согласованы до реализации.

## 20. Требования к unit-тестам

Unit-тесты должны проверять отдельные правила и переходы состояния.

Минимальный набор направлений:

- проверка допустимых диапазонов;
- изменение контакта;
- изменение сопротивления;
- изменение продвижения;
- регистрация критической ошибки;
- потеря контакта;
- восстановление контакта;
- условия завершения;
- использование подсказок;
- расчёт независимых результатов;
- расчёт итоговой формулы;
- параметры сложности.

Примеры тестов:

| Тест | Ожидаемый результат |
|---|---|
| Контакт увеличивается | Значение изменяется по правилу |
| Контакт достигает нижней границы | Значение не выходит за диапазон |
| Продвижение увеличивается | Значение соответствует событию |
| Критическая ошибка | Регистрируется соответствующее событие |
| Потеря контакта | Выполняется утверждённый переход |
| Использование подсказки | Событие регистрируется |
| Одинаковые входные данные | Одинаковый результат |

Фактические тестовые значения должны быть добавлены после утверждения числовых правил.
